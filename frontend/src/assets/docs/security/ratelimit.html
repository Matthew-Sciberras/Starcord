What is a rate limit

Rate-limits Explained

You may be wondering, what is a rate limit? Well I'm glad you asked

Put simply, ratelimits are a way to limit the number of requests someone can do to your server, in a given amount of time

This can be done, not only for normal users, when little Timmy decides that a loading animation means spam the login button 20 more times, but it also is there for bad actors, such as hackers, who try to DDOS your server, or other methods.

"woah Matthew, whats a DDOS?", well, DDOS, the abbreviation for a Distributed Denial of Service Attack, is when a hacker uses multiple devices to send hundreds of thousands of requests, sometimes even millions, all to your tiny server.

Let's take an example where they are attempting to target the /login endpoint. Each login request goes through a controller, service, repository, makes multiple calls to a database, goes through many helper functions, and more. All this is very costly for the server, so, it starts to back up requests for your normal users, which makes the website slow.

If the traffic is too much to handle, the server may even crash, causing your entire application to go temporarily unavailable.

Obviously, this is a big no no in the world of cybersecurity, so we add ratelimits. Rate limiting is very cheap, in terms of server resources, usually only passing through a controller and a cache, nothing major. If the cache realizes that the user has exceeded the maximum number of requests for that endpoint, the request instantly gets cut off, no need for any expensive database calls.

Caching

What is caching?

In the previous section, I mentioned a little thing called caching. Already know what that is? Feel free to skip to the next question

Oh you're still reading? Great. Let me explain to you how caching works.

All data, be it text, numbers, booleans, etc, are all stored somewhere. Some are stored in long-term storage, which, if the server restarts, will not loose it's data, this is usually done through a database (or if you're lazy a text/json file)

On the other hand, we have short-term memory (caching). This data is lost when the server is restarted, so it's good for storing things that need to be kept for a short amount of time.

So, you may ask, why don't we just use long term for everything? One problem, it's incredibly slow and costly (relative). It's still only a few hundred ms, but caching is so fast, it's usually measured in nanoseconds (1 millisecond is 1000000 nanoseconds).

Since it's incredibly fast, it adds little to no latency to our API's, which is why it's perfect for rate limiting. It allows very fast inputting and fetching of data, which means all requests won't feel bulky, and it also is fine if that data is lost after a restart.

So, to recap, caching go brrrrr like Lightning Mcqueen, but has the memory of a goldfish. Databases are slow like Lance Stroll, but at least they remember things.

Redis Caching

Redis

Okay good, now you know what caching is. Now, question is, how do we cache?

Caching comes in many different forms, your computer RAM is a form of a cache, your CPU has a cache, etc. But, in Starcord, I opted for a more structured cache.

I decided to use the popular caching "database" called Redis

Redis, has all the advantages of the lightning fast cache, while also giving you a structured way to store that data, rather than storing it in a variable in memory. Redis allows you to have tables, which structures the data much better, and makes it easier to access

Put simply, Redis takes caching, and makes it easier to deal with. Rather than playing around with memory (poor C developers), or else using plain variables, it's a much better way to store your caching data, and also faster.

IP Logging

IP Logging in Starcord

As you should know, every web page you access has the ability to access your IP. This is why it's important to be careful which websites you visit kids!

Now me personally, I'm not interested in seeing where Little Timmy lives. But, I do want to make sure that Little Timmy doesn't spam my endpoints and attempt to break the server

One way to do this, would be to store the amount of requests per account. This creates an issue though. Web pages are slow because you need to render data, consoles, which hackers opt for, are not as slow. You can also run multiple requests concurrently (together) to make even more requests, and you can do so with multiple accounts, rendering this method useless.

The second option, more widely used, is to ratelimit based on the users IP. Since the data is not stored, rather just cached, you do not have to worry about your IP getting leaked to the internet. This option is more widely used, because even if Little Timmy has 5 computers at home, they're all registered under the same IP, rendering his so called DDOS useless.

You may tell me "can he not just use a VPN?", answer is, yes. VPN's can technically bypass this limitation, but seeing as Starcord is open source, and not designed for mass public use, I cannot be asked to go into more restrictive, and annoying measures, which can also sometimes raise false positives, giving an annoying user experience (cough cough Discord logins)

Ratelimits in the backend

In the back end (pause)

In the Spring backend, the rate limit's themselves are stored in the redis cache like we had said, in the form ratelimit:clientIp:methodName. This allows the ratelimit to be checked per ip, per name

Different methods of course have different ratelimits. A presence GET request should have more leniency than a login request, as you may need to get the presence of many users, but should only realistically be logging in at most 3 times in a minute

Of course, I didn't set the hard limit to be at the "realistically" point, we gave a bit of breathing room, just in case you logged in the wrong account 5 times for example

Of course, the source code is all public, so you can go check the ratelimits for each API yourself, but they are also listed in each endpoint's docs, on the left hand side of your screen (i feel like a flight attendant showing you the emergency exits!)

To dive a bit more into the technical side, the actual ratelimits are handled by an annotation, and a rate limit service

The annotation, written as @Ratelimit(limit=x), is annotated on top of every controller method. There is also an optional parameter for timeWindowSeconds which allows you to change the amount of time before the ratelimit resets, but the default for this is 60s

That limit is then passed onto the Ratelimit aspect class, who is like the bodyguard, checking if your request is allowed before it even reaches the service level. The Ratelimit aspect class calls one service, the RateLimitService (very original I know) to actually check if the user has exceeded the ratelimit amount, and if so, reject the request
